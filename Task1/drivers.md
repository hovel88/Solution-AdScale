# Определение архитектурных драйверов

## Бизнес-драйверы

Согласно постановке задания, основные цели, для чего бизнес хочет провести изменения в системе:

1. Интеграция с крупной DSP-площадкой. Необходимо технически и организационно обеспечить подключение нового крупного партнера.
2. Обеспечить мультиплатформенную интеграцию, для будущего легкого подключения новых площадок.
3. Удержать клиентов. Текущие клиенты не должны пострадать из-за роста нагрузки.
4. Избежать штрафов и не потерять выручку из-за проигранных аукционов.

## Функциональные требования

Система должна выполнять следующие функциональные требования (Functional Requirements).

| ## | Требование |
| -- | -- |
| FR-01 | Принимать Bid Requests, обрабатывать их и отдавать Bid Responses (OpenRTB) |
| FR-02 | Определять пользователя, подбирать кандидатов в рекламу |
| FR-03 | Применять бизнес-правила, бюджеты и таргетинг для выбора победителя RTB-аукциона |
| FR-04 | Интеграция с несколькими DSP-партнёрами одновременно |
| FR-05 | Мультиплатформенность. Возможность дальнейшего подключения новых DSP без существенной переработки архитектуры. |
| FR-06 | Возможность рекламодателям управлять кампаниями, бюджетами и ставками через личный кабинет |
| FR-07 | Предоставлять рекламодателям аналитические отчеты по кампаниям |
| FR-08 | Обеспечивать точность и идемпотентность списания средств, выставления счетов, управление балансами |
| FR-09 | Сохранение статистики кликов и показов рекламы |

## Атрибуты качества (нефункциональные требования)

С учетом приоритизации по бизнес-целям (что важнее всего для проекта), система должна обеспечивать нефункциональные требования (Non-Functional Requirements).

| ## | Атрибут качества | Метрика | Приоритет |
| -- | -- | -- | -- |
| NFR-01 | Низкая задержка | P95 <100 мс на аукцион, а для ответа DSP - <80 мс. Сейчас у нас 110-120 мс | Критический |
| NFR-02 | Производительность | Выдержать 18k RPS (через 3 мес) и 50k RPS (через год). Сейчас у нас 15к RPS | Критический |
| NFR-03 | Масштабируемость | Горизонтальное масштабирование наиболее нагруженных компонентов и мультирегиональное развёртывание | Высокий |
| NFR-04 | Доступность | Минимизация простоев и исключение единой точки отказа. SLA 99,9% в целевой архитектуре | Высокий |
| NFR-05 | Согласованность данных | Финансовые операции не должны теряться или дублироваться | Высокий |
| NFR-06 | Надежность | Сохранение корректной обработки ставок и событий даже при отказах отдельных компонентов | Высокий |
| NFR-07 | Отказоустойчивость | Должны быть изолированы сбои (Fault Tolerance), никаких каскадных падений, автоматическое восстановление сервисов | Высокий |
| NFR-08 | Безопасность | Защита API, финансовых операций, персональных данных (если есть), каналов взаимодействия с внешними системами, и внутреннего контура | Средний |
| NFR-09 | Удобство разработки и поставки | Возможность независимого деплоя компонентов | Средний |
| NFR-10 | Модифицируемость | Возможность постепенного эволюционного преобразования монолита в микросервисы, переход к событийно-ориентированной обработке | Средний |
| NFR-11 | Наблюдаемость | Метрики, логи, трейсинг. Удобство и скорость отладки и диагностирования проблем распределенной системы | Средний |

## Ограничения

По постановке задачи проекта, решение должно учитывать некоторые ограничения бизнес характера (Business Constraints) и технического характера (Technical Constraints).

**Существующие бизнес-ограничения**:

| ## | Ограничение | Описание |
| -- | -- | -- |
| BC-01 | Срок | Необходима поэтапная эволюция системы, при этом на промежуточное решение (интеграцию с новой DSP площадкой) выделено всего 3 месяца |
| BC-02 | Бюджет | Из-за того, что бюджет ограничен, по возможности, надо переиспользовать функции самого монолита, вынося из него лишь критические компоненты |
| BC-03 | Непрерывность | По условию, мы обязаны не допускать простоев и удержать текущих клиентов |
| BC-04 | Кадры | В штате 35 человек: backend-, frontend- и DevOps-разработчики, тестировщики, дизайнеры, сотрудники службы поддержки и менеджмент. Выделенных SRE-инженера, технического писателя и бизнес-аналитика в компании нет. Значит архитектура должна быть понятной для текущей команды |

**Существующие техничские ограничения**:

| ## | Ограничение | Описание |
| -- | -- | -- |
| TC-01 | Инфраструктура | Сейчас только один production-кластер, деплой производится руками без контейнеризации. Это усложняет масштабирование и замедляет выпуск изменений |
| TC-02 | Legacy | Существующий гибридный монолит написан на C++/Go/Python/Node. Это ограничивает независимое масштабирование компонентов |
| TC-03 | Минимальные изменения | В связи ограниченным бюджетом, сроками и кадрами, для промежуточного этапа желательно воздержаться от кардинальных изменений. Несмотря на все минусы одного инстанса БД и отсутствия High Availability, из-за невозможности переписать legacy монолит, нужно переиспользовать это решение, минимизируя негативные последствия |
