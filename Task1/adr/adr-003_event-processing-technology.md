# ADR-003. Выбор технологии для потоковой обработки событий

**Статус:** Принято (2026-08-27)  
**Автор**:  

## Контекст

После анализа существующей архитектуры, выло выявлено, что имеется синхронная запись событий (клики, показы) в основную транзакционную БД. Это создает недопустимую нагрузку на I/O и мешает масштабированию.

В целевой архитектуре необходимо разорвать синхронную связь между Delivery Service и хранилищем данных. Для этого вводится система обмена сообщениями (Message Broker). Мы должны выбрать брокер, который позволит:

1. Выдержать пиковые нагрузки на систему (добавить свойство Backpressure).

2. Обеспечить долговременное хранение потока событий для аналитики и потенциальной её переобработки (Replay).

3. Интегрироваться с экосистемой больших данных (ClickHouse, аналитические пайплайны).

## Решение

Выбрали вариант 4 - использование **Apache Kafka** в качестве распределенного лога событий (distributed log) и центрального хаба потоковой передачи данных.

## Рассмотренные альтернативы

### Альтернатива 1. Ничего не менять, писать напрямую в БД

**Плюсы:**

* простая реализация;
* не усложняется архитектура;
* отсутствуют затраты на миграцию.

**Минусы:**

* увеличивается нагрузка на PostgreSQL;
* обработку событий масштабировать затруднительно;
* уже наблюдается сейчас деградация latency (запись статистики по кликам и просмотрам, это всё тот же Noisy Neighbor);
* уже наблюдается сейчас провал про SLA.

### Альтернатива 2. Использовать RabbitMQ

**Плюсы:**

* отличная поддержка сложной маршрутизации (exchanges, routing keys);
* зрелый инструмент на базе протокола AMQP, много информации и поддержки;
* прост в эксплуатации;
* позволяет реализовать асинхронную обработку.

**Минусы:**

* ориентирован на парадигму "умный брокер, глупый потребитель", поэтому отлично подходит для RPC/команд, но не для бесконечного потока логов;
* хранение сообщений на диске не предназначено для очень длительного хранения больших объемов;
* не удобен для построения аналитических потоков и менее эффективен при очень больших потоках событий (до нескольких десятков тысяч сообщений в секунду);
* сложнее настраивать Replay (повторное чтение исторических данных) и масштабирование партиций на лету.

### Альтернатива 3. Использовать NATS / NATS JetStream

**Плюсы:**

* очень быстрый;
* минимальные задержки (latency) - для системы это критически важно, но не в плане потока статистики;
* невероятно прост в эксплуатации (один бинарник, мало компонентов);
* потребляет мало ресурсов;
* имеет высокую производительность, сравнимую с Kafka (более сотни тысяч сообщений в секунду);
* можно подключать несколько независимых потребителей данных;
* идеален для Cloud Native уведомлений и ephemeral-событий.

**Минусы:**

* гарантии хранения (Durability) только в расширении JetStream и появились относительно недавно;
* уступает Kafka в зрелости при работе с большими объемами данных;
* больше подходит для доставки сообщений с возможностью Replay, но не как распределенный лог событий.

### Альтернатива 4. Использовать Kafka

**Плюсы:**

* очень зрелый продукт с большим количеством информации и экспертизы;
* крайне высокая пропускная способность;
* очень развитые возможности в горизонтальном масштабировании обработки данных;
* данные хранятся в партициях заданное время (retention);
* возможность повторного чтения сообщений (например, аналитический сервис может перечитать вчерашние события, если у него была ошибка в логике);
* можно подключать несколько независимых потребителей данных;
* развитая экосистема, де-факто стандарт для event-streaming. Легко подключать ClickHouse, Spark, Flink и т.д.

**Минусы:**

* требует умения его настраивать и администрировать и сопровождать, что увеличивает операционную нагрузку;
* увеличивает сложность инфраструктуры;
* избыточен для простых задач.

## Последствия

### Положительные

* уменьшается нагрузка на PostgreSQL;
* обработка статистики извлекается из критического пути обработки запросов;
* способствует достижению требуемого SLA по доступности, производительности и задержкам;
* увеличивается устойчивость системы к пиковым нагрузкам;
* возможность независимого масштабирования;
* достигается одна из целей - построение событийно-ориентированной архитектуры.

### Отрицательные

* увеличение сложности архитектуры;
* увеличение количества интеграционных взаимодействий;
* усложняется тестирование и мониторинг;
* требуется сопровождение Kafka-кластера.

### Риски

* необходимо обеспечить идемпотентную обработку событий для исключения ошибок при повторной доставке, иначе нарушатся функциональные требования;
* отказ потребителей может привести к накоплению очередей сообщений и увеличению времени обработки статистики, однако это плата за повышение устойчивости системы;
* нужно иметь определенный уровень экспертизы для администрирования и настройки Kafka-кластера, иначе можно ухудшить производительность системы.

## Примечание

У решения имеются и следующие последствия, которые нужно учесть для последующей проработки архитектурных решений.

1. Разработчикам придется привыкнуть к новой парадигме (Producer/Consumer Groups, Offset).

2. Необходимо продумать схемы данных, вероятно, использование Schema Registry (Avro).

3. Однако, это позволит заметно улучшить устойчивость системы (буферизация событий).

## Контроль

Проверять, что решение соблюдается будем через архитектурные артефакты и реализацию системы.
