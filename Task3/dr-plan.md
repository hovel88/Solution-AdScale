# Disaster Recovery Plan (DRP)

## Сценарий 1: Отказ одной зоны доступности (Availability Zone Failure)

**Вероятность:** Средняя (отказ ЦОД, сетевая изоляция)  
**Влияние:** Потеря части реплик, деградация чтения

**Действия:**

1. **Детекция:** Мониторинг фиксирует недоступность узлов в зоне A (Prometheus alert: `az_down`)
2. **Failover:**
   * PostgreSQL (Patroni): автоматическое переключение Master на реплику в зоне B (RTO < 1 мин)
   * Redis Sentinel: повышение Slave в зоне B до Master (RTO < 30 сек)
   * Kafka: переключение лидеров партиций на брокеры в зоне B (автоматически)
3. **Проверка:** Health-check сервисов в зоне B
4. **Уведомление:** Дежурный инженер + бизнес-стейкхолдеры

**Failback:**

* После восстановления зоны A: синхронизация реплик, возврат лидерства (ручной или по расписанию)

## Сценарий 2: Потеря региона (Region Failure)

**Вероятность:** Низкая (стихийное бедствие, отключение всего ДЦ)  
**Влияние:** Полная остановка сервиса

**Действия:**

1. **Детекция:** Мониторинг фиксирует недоступность всего региона
2. **Failover на резервный регион:**
   * DNS переключение на standby-регион (TTL заранее снижен до 60 сек)
   * Запуск сервисов в standby-регионе (IaC: Terraform apply)
   * Восстановление данных из offsite-бэкапов
3. **RTO:** < 4 часов (целевое)
4. **RPO:** < 1 час (бэкапы каждые 15 минут)

**Failback:**

* После восстановления основного региона: синхронизация данных, переключение трафика обратно

## Offsite-бэкапы

| Компонент | Частота | Хранение | Регион |
| -- | -- | -- | -- |
| PostgreSQL | Каждые 15 мин (WAL) + ежедневно (full) | S3 (Glacier) | Отдельный регион |
| ClickHouse | Ежедневно | S3 | Отдельный регион |
| Redis | RDB каждые 5 мин | S3 | Отдельный регион |
| Kafka | Retention 7-30 дней | Диски брокеров | Репликация RF=3 |

## Тестирование восстановления

| Тест | Частота | Ответственный |
| -- | -- | -- |
| Восстановление PG из бэкапа | Ежемесячно | DBA |
| Переключение на standby-регион | Ежеквартально | SRE |
| Chaos Engineering (отказ узла) | Еженедельно | DevOps |
