# Масштабирование баз данных - Database Scaling Strategy

## Назначение документа

Документ описывает стратегию масштабирования баз данных микросервисной архитектуры DSP-платформы. Для каждого сервиса определены подходы к репликации, шардированию, использованию Read Replicas, необходимость применения паттерна CQRS. Выстраиваем стратегию: что будет, когда вырастет нагрузка.

## 1. Репликация (Master-Slave)

**Обоснование**: необходимо для снятия нагрузки на чтение и повышения доступности.

| Тип | Описание |
| -- | -- |
| **PostgreSQL (Financial Service)** | Master принимает запись (списания), Slave используется для чтения (отчеты). Обеспечивает HA (Patroni). Также репликация обеспечивает быстрое восстановление при отказе, что важно для финансовых данных. |
| **PostgreSQL (Campaign Service)** | Большинство операций — чтение настроек кампаний. Реплики снижают нагрузку на основную БД. |
| **Redis** | Master-Slave + Sentinel для обеспечения failover, повышения доступности и отказоустойчивости. |
| **ClickHouse** | Используется ReplicatedMergeTree. Аналитические запросы распределяются между несколькими репликами для повышения производительности. Также обеспечивается HA и защита от потери событий при отказе узла. |

## 2. Шардирование (Sharding)

**Обоснование**: если данные не влезают на один диск или одна нода не выдерживает нагрузку, повышает возможности масштабирования.

**Важно**: Bidding Service не шардируется, он масштабируется горизонтально, потому что держит данные в Redis.

| Тип | Описание |
| -- | -- |
| **Kafka** | Партиционирование топиков по ключу события (`event_id` или `campaign_id`). Это не совсем шадрирование, но близкое. |
| **ClickHouse** | Шардирование по `advertiser_id` или `event_date`. Это позволяет быстро выбирать данные за период (ускоряет агрегацию) и обеспечивает равномерное распределение событий.<br>**В данном случае шардирование действительно очень важно!** |
| **Redis** | Шардирование через Redis Cluster (слоты). Ключ: `campaign_id`.<br>**Однако количество кампаний значительно меньше количества событий, поэтому масштабирования может быть достаточно и шардирования не потребуется!** |
| **PostgreSQL** | Финансовые операции требуют строгой согласованности данных, поэтому шардирование усложнило бы обеспечение транзакционной целостности.<br>**В данном случае шадрирование принесет больше сложностей и не рекомендуется** |

## 3. Read Replicas

**Обоснование**: используются для сервисов, в которых операции чтения существенно превышают количество операций записи. Мы создаем физическую копию той же БД, чтобы разгрузить Master-узел для чтения. А все операции изменения данных выполняются только через Master-узел.

Отличие **CQRS** от **Read Replicas** в уровне: CQRS — паттерн на уровне архитектуры и кода, Read Replicas — мера на уровне инфраструктуры (БД).

| Сервис | Применение |
| -- | -- |
| **PostgreSQL** (Finance Service) | Реплики используются для формирования финансовых отчетов, чтобы тяжелые SELECT'ы не конкурировали с транзакциями списания |
| **PostgreSQL** (Campaign Service) | Реплики используются для Cache Warming (прогрева Redis) при старте Bidding Service |
| **ClickHouse** | Реплики используются для отказоустойчивости и параллельного выполнения аналитических запросов |

**Важно:** Запись всегда выполняется только через Master. Если требуется чтение "свежих" данных (только что записанных), такие операции направляются принудительно на Master, чтобы избежать рассинхронизации.

## 4. CQRS (Command Query Responsibility Segregation)

**Обоснование**: зачастую применятся, чтобы сложные аналитические запросы (модель чтения) не блокировали транзакции (модель записи), также для отделения процесса аудита. Т.е. тот случай, когда нагрузка на чтение может значительно превышать нагрузку на запись и для этого мы разделяем логику записи и чтения на уровне кода и моделей данных.

Отличие **CQRS** от **Read Replicas** в уровне: CQRS — паттерн на уровне архитектуры и кода, Read Replicas — на уровне инфраструктуры (БД).

| Сервис | CQRS | Обоснование |
| -- | -- | -- |
| Bidding Service | Нет | Работает с материализованным представлением в In-Memory (Redis) в режиме Read-Only |
| Campaign Service | Да (в перспективе) | Запись и изменение рекламных кампаний происходит редко, а чтение выполняется значительно чаще. Однако в целевой архитектуре сервис пока остается в составе Legacy монолита |
| Statistics Service | Нет | Потоковая запись уже отделена от аналитических запросов через Kafka |
| Analytics Service | Нет | Все запросы — чтение. Читает агрегаты из ClickHouse |
| Finance Service | Да | Команды (списания) идут в PostgreSQL, а отчеты и аудит используют отдельную модель чтения (ClickHouse/Read Replica) |
