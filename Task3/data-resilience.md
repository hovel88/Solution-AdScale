# Отказоустойчивость данных

## Назначение документа

Документ описывает стратегию обеспечения отказоустойчивости данных в DSP-платформе. Рассматриваются целевые показатели восстановления (RPO и RTO), стратегия резервного копирования и соответствие принципам 12-факторных приложений.

## RPO и RTO

Для каждого сервиса определены допустимые значения RPO (Recovery Point Objective) и RTO (Recovery Time Objective).

* **RPO** — максимально допустимая потеря данных.
* **RTO** — максимально допустимое время восстановления работы сервиса.

| Сервис | RPO | RTO | Стратегия |
| -- | -- | -- | -- |
| Financial Service (PostgreSQL) | 0 | < 1 мин | Синхронная репликация, Patroni |
| Campaign Service (PostgreSQL) | 0 | < 5 мин | Master-Slave |
| Bidding Service (Redis) | ~0 | < 1 мин | Redis Sentinel |
| Events Service (Kafka) | 0 | < 1 мин | Репликация (RF=3) |
| Analytics Service (ClickHouse) | < 24 ч | < 4 часов | Данные в Kafka, перезаливка |

Сценарии и планы восстановления описаны в [документе](./dr-plan.md).

## Обеспечение отказоустойчивости

Для повышения надежности используются следующие решения:

* репликация баз данных
* регулярное резервное копирование
* использование Kafka для надежной передачи событий
* автоматический перезапуск сервисов средствами контейнерной платформы.

При отказе одного из компонентов система продолжает работу, а после восстановления синхронизирует данные.

## Стратегия резервного копирования

Для хранения данных используется комбинированная стратегия резервного копирования.

### PostgreSQL

Для сервисов Campaign Service и Finance Service выполняются:

* ежедневное полное резервное копирование
* регулярное резервное копирование журналов транзакций
* хранение нескольких последних резервных копий.

Такой подход обеспечивает восстанавливаемость данных в случае сбоя или ошибки.

### ClickHouse

Для сервисов Statistics Service и Analytics Service выполняются:

* ежедневные резервные копии данных
* репликация между узлами кластера
* восстановление из резервной копии при необходимости.

Такой подход обеспечивает сохранность статистических данных и аналитической информации.

### Соответствие принципам 12-факторных приложений

Архитектура соответствует основным принципам 12-факторных приложений.

| Принцип | Реализация |
| -- | -- |
| **1. Codebase** | Каждый микросервис имеет собственный репозиторий |
| **2. Dependencies** | Зависимости явно описываются и устанавливаются при сборке |
| **3. Config** | Конфигурация хранится в переменных окружения |
| **4. Backing Services** | Базы данных и брокеры подключаются как внешние ресурсы |
| **5. Build, Release, Run** | CI/CD pipeline, контейнеризация |
| **6. Processes** | Сервисы stateless, состояние вынесено в Redis/PostgreSQL (не касается оставшегося Legacy монолита) |
| **7. Port Binding** | Каждый сервис предоставляет API через порт (например gRPC, REST-API) |
| **8. Concurrency** | Горизонтальное масштабирование запуском новых контейнеров |
| **9. Disposability** | Контейнеризация, быстрый старт и корректная остановка |
| **10. Dev/Prod Parity** | Одинаковые технологии во всех средах |
| **11. Logs** | Логи пишутся в stdout и собираются централизованно |
| **12. Admin Processes** | Миграции, прогрев кэша, служебные скрипты выполняются отдельно |
