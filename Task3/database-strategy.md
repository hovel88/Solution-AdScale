# Database per Service - Выбор базы данных для каждого сервиса

## Назначение документа

Документ описывает стратегию хранения данных для микросервисной архитектуры DSP-платформы. Для каждого сервиса выбрана собственная база данных в соответствии с паттерном **Database per Service**. Это позволяет изолировать отказы: если "легла" одна БД, остальные сервисы продолжают работать.

Выбор СУБД основан на характере нагрузки, требованиях к согласованности данных, производительности и масштабируемости. Каждый сервис владеет своими данными и не имеет доступа в чужие таблицы. Такой подход уменьшает связанность компонентов и позволяет независимо развивать и масштабировать сервисы.

## Выбор баз данных

| Сервис | Тип базы данных | Обоснование |
| -- | -- | -- |
| **Bidding Service** (Сервис ставок) | Redis (In-Memory) | Это Hot Path. Ему нужна скорость меньше миллисекунды. Данные о кампаниях и ставках должны быть уже в оперативной памяти (материализованное представление). Дисковые БД (SQL/NoSQL) слишком медленные. |
| **Campaign Service** (Сервис кампаний) | PostgreSQL (Реляционная) | Кампании имеют строгую структуру, связи (рекламодатель -> кампания -> креатив) и требуют транзакций ACID при создании/редактировании. Плюс, нам нужна надежность и возможность делать сложные выборки. Сервис кампаний управляет жизненным циклом рекламных кампаний, он владеет этими данными, а материализация в In-Memory для сервиса ставок происходит посредством CDC. |
| **Statistics Service** (Сервис статистики) | Kafka + ClickHouse | События кликов/показов — это огромный непрерывны поток. Количество записей может достигать миллиардов событий в сутки. Сначала пишем в Kafka (буфер), затем батчами в ClickHouse. ClickHouse идеален для аналитических запросов по миллионам строк. Он обеспечивает эффективное хранение временных рядов. |
| **Analytics Service** (Сервис аналитики) | ClickHouse | Сервис использует накопленную статистику для формирования BI-отчетов, дашбордов и т.д. Для этого читает агрегированные данные. Ему не нужны транзакции, ему нужны быстрые выборки (основная нагрузка состоит из сложных аналитических запросов - OLAP). ClickHouse справляется с этим лучше, чем PostgreSQL. |
| **Financial Service** (Сервис финансов) | PostgreSQL (Реляционная) | Работа с деньгами (выставление счетов, ведение бюджета кампаний и баланса рекламодателей, финансовый журнал операций) — только ACID. Никаких NoSQL. Любая потеря данных недопустима. Здесь нужна строгая согласованность, транзакции, аудит и возможность блокировок. |

**Примечание**: БД для сервиса кампаний (Campaign Service) и для сервиса финансов (Financial Service) — PostgreSQL. В рамках целевой архитектуры данные кампаний и финансов физически разделены на разные инстансы PostgreSQL, даже если сами сервисы пока остаются в Legacy монолите и не вынесены по отдельным микросервисам посредством паттерна **Strangler Fig**. Это необходимо для независимого масштабирования и изоляции нагрузки.

## Итоговая стратегия хранения данных

| Характер нагрузки | База данных | Сервисы |
| -- | -- | -- |
| **OLTP (транзакционная)** | PostgreSQL | Campaign Service, Finance Service |
| **OLAP (аналитическая)** | ClickHouse | Statistics Service, Analytics Service |
| **Event Streaming (потоковая)** | Kafka | Statistics Service, Billing (часть Finance Service) |
| **In-Memory (Hot Path)** | Redis | Bidding Service |
