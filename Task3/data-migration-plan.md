# План миграции данных (Backfill, CDC, Cutover, Rollback)

Целевое архитектурное решение подразумевает вынос данных из общей БД PostgreSQL в отдельные сервисы, поэтому нужен план миграции.

## Фазы

### Фаза 1: Backfill (перенос исторических данных)

1. Создать целевую схему в новом сервисе (например, Campaign Service)
2. Написать скрипт миграции: SELECT из legacy -> INSERT в новый
3. Запустить миграцию в фоновом режиме (не блокируя production)
4. Верификация: сравнить row counts, checksums

### Фаза 2: CDC (синхронизация в реальном времени)

1. Включить Debezium на legacy PostgreSQL
2. Настроить поток CDC: legacy -> Kafka -> новый сервис
3. Двойная запись: новые изменения пишутся и в legacy, и в новый сервис
4. Мониторинг: отставание CDC, ошибки

### Фаза 3: Cutover (переключение трафика)

1. Shadow-read: читать из нового сервиса, сравнивать с legacy
2. Если данные совпадают — переключить чтение на новый сервис
3. Остановить запись в legacy
4. Убрать CDC

### Фаза 4: Rollback (откат при проблемах)

1. Если новый сервис деградирует — вернуть чтение на legacy
2. Данные за время работы нового сервиса — синхронизировать обратно
3. Исправить проблему и повторить cutover
