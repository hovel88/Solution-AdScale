# Дизайн кэширования - Caching Strategy

## Назначение документа

Документ описывает стратегию кэширования данных в микросервисной архитектуре DSP-платформы. Использование Redis позволяет снизить нагрузку на базы данных, уменьшить задержки при обработке RTB-аукционов и повысить общую производительность системы.

## Объекты кеширования

| Данные | Почему |
| -- | -- |
| Кампании | Статусы, правила таргетинга. Они меняются редко, используются практически при каждом RTB-аукционе |
| Бюджеты | Лимиты на кампанию и на отдельные ставки. Проверяются перед размещением ставки. Быстрое чтение снижает задержку принятия решения |
| Настройки ставок | Используются алгоритмом выбора ставки и изменяются значительно реже, чем читаются |
| Настройки таргетинга | География, устройства, браузеры и другие параметры активно используются при фильтрации кампаний |
| Креативы | Ссылки на рекламный контент |

## Размещение

Отдельный кластер Redis, максимально близко к Bidding Service (в идеале в одной подсети/зоне доступности).

Кластер состоит из

* Redis Cluster;
* несколько Primary-узлов;
* Replica для каждого Primary;
* Sentinel (или встроенные механизмы Redis Cluster) для автоматического переключения при отказе.

## TTL и стратегия инвалидации

TTL выбирается исходя из частоты изменения данных: редко изменяемые данные кэшируются дольше, а критичные данные имеют минимальное время жизни.

| Данные | TTL |
| -- | -- |
| Кампании | 10 минут |
| Бюджеты | 5 минут<br>**в нормальном режиме — живет до инвалидации (для этого показателя критичнее инвалидация, а TTL как страховка)** |
| Настройки ставок | 5 минут |
| Настройки таргетинга | 30 минут |
| Креативы | 10 минут |

**Инвалидация**: событийная (Event-Driven). Когда рекламодатель меняет кампанию (через Dashboard -> PostgreSQL), срабатывает CDC (Debezium), который ловит изменение и отправляет команду на изменение в Redis.  
Инвалидация должна происходить синхронно с записью в PostgreSQL. Изменение сначала валидируется, затем пишется в БД и только потом (или одновременно) публикуется событие в Redis.

В дополнение, для устранения проблем с устареванием данных в кэше, применяется механизм **версионирования данных** (optimistic locking). Каждая запись в PostgreSQL имеет поле `version`.  
Когда CDC передает изменение в Redis, он передает и версию (которая увеличивается при каждом изменении данных в строке таблицы).  

Пример записей:

```yaml
# В PostgreSQL
campaign:
  id: 123
  budget_limit: 9500
  version: 42

# В Redis
campaign:123:
  budget_limit: 10000
  source_version: 41
```

CDC отправляет обновление, при обновлении Redis проверяется, если version из PostgreSQL новее, то данные обновляются, иначе - игнорируется (устаревшее событие).

## Прогрев кэша (Cache Warming)

Bidding Service для своей работы должен иметь материализованное представление данных из PostgreSQL в Redis.

Прогрев выполняется:

* **При старте приложения (холодный старт)**  
  Прогрев обязателен. Иначе первые запросы пойдут в пустоту.
* **После восстановления Redis (failover)**  
  Прогрев обязателен. Когда поднялся новый мастер, он пустой.

**Реализация**: отдельный сервис (или init-container) делает SELECT из PostgreSQL (желательно с Read Replica, чтобы не нагружать Master) и загружает данные в Redis.
