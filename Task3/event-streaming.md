# Потоковая обработка данных

## Назначение документа

Документ описывает архитектуру потоковой обработки событий в DSP-платформе. Для обмена потоковыми сообщениями используется Apache Kafka. Это позволяет организовать асинхронное взаимодействие сервисов, уменьшить их связанность и обеспечить обработку большого количества событий в режиме реального времени.

## Топики Kafka

| Топик | Описание | Ключ партиции |
| -- | -- | -- |
| `impressions` | События показов | `event_id` |
| `clicks` | События кликов | `event_id` |
| `billing.events` | События для финансового сервиса | `campaign_id` |

## Формат сообщений

Для схемы сообщений используется **Avro**. Это бинарный формат, компактный, поддерживает эволюцию схемы.

Для управления версиями схем используется **Schema Registry**. Это критично при независимом развитии сервисов. Это позволяет:

* избежать конфликтов при изменении структуры событий
* отслеживать эволюцию контрактов
* автоматически валидировать сообщения на стороне продюсера и потребителя.

Пример структуры события (для наглядности, в читаемом виде):

```yaml
event_id: "UUID-EV-111"
campaign_id: "UUID-CAM-222"
creative_id: "UUID-CRE-333"
user_id: "UUID-USR-444"
event_type: click
timestamp: "2026-09-09T16:13:00Z"
price: 1.23
currency: "USD"
```

## Группы потребителей (Consumer Groups)

Для каждого микросервиса создается собственная группа потребителей (Consumer Group). Использование Consumer Groups позволяет распределять сообщения между несколькими экземплярами одного сервиса, повышая производительность и отказоустойчивость.

| Consumer Group | Описание |
| -- | -- |
| `group.clickhouse` | читает `impressions` и `clicks`, пишет батчами в ClickHouse |
| `group.billing` | читает `impressions`, списывает деньги |
| `group.analytics` | читает события для построения отчетов в реальном времени |

## Политика хранения (Retention)

Срок хранения зависит от назначения данных:

* статистические данные сохраняются дольше для формирования отчетов
* финансовые события имеют увеличенный срок хранения для проведения аудита

| Топик | Время хранения |
| -- | -- |
| `impressions` | 7 дней (для возможности Replay и пересчета аналитики) |
| `clicks` | 7 дней (для возможности Replay и пересчета аналитики) |
| `billing.events` | 30 дней (для финансового аудита) |

## Надежность доставки

Для повышения надежности используются следующие механизмы:

* репликация данных между брокерами Kafka
* автоматическое восстановление после отказа брокера
* подтверждение получения сообщений потребителями
* повторная обработка сообщений при временных ошибках.

Конфигурация кластера и гарантии доставки:

| Параметр | Значение | Обоснование |
| -- | -- | -- |
| `replication.factor` | 3 | Хранение данных на трёх узлах, защита от потери |
| `acks` | all | Продюсер ждёт подтверждения от всех реплик |
| `min.insync.replicas` | 2 | Баланс между надёжностью и доступностью |
| `enable.idempotence` | true | Предотвращение дубликатов на стороне продюсера |

Это гарантирует доставку **at least once** на уровне Kafka. Поэтому все потребители обязаны обеспечивать идемпотентную обработку (см. [`reliability.md`](../Task2/reliability.md)).
