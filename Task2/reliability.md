# Надёжность (Reliability)

Цель раздела — определить поведение системы при отказах, чтобы обеспечить SLA 99.9% и сохранить бизнес-показатели (выручку, репутацию) даже при частичной деградации компонентов.

RTB-платформа должна сохранять стабильность при высокой нагрузке и частичных отказах. Bidding Service является критическим компонентом, так как участвует в аукционе в реальном времени.

Основные требования к надёжности:

* Время ответа Bid Request: P95 < 100 мс.
* Отсутствие единой точки отказа (SPOF).
* Сохранение работоспособности при деградации зависимых сервисов.
* Предотвращение финансовых ошибок.
* Горизонтальное масштабирование.
* Недопущение блокировки критического пути (Hot Path).

Для достижения этих целей применяются паттерны:

* Circuit Breaker.
* Deadline и ограниченные Retry.
* Идемпотентность операций.
* Fallback стратегии.
* Отказоустойчивые конфигурации Kafka и Redis.

## Паттерны надёжности (по уровням)

| Уровень | Паттерн | Где применяется |
| -- | -- | -- |
| Транспорт | Rate Limiting, Circuit Breaker | API Gateway -> Bidding |
| Сервисы | Timeout, Retry, Fallback | Bidding, Delivery |
| Данные | Идемпотентность, Outbox | События, Финансы |

## 1. Deadline и Timeout

Deadline — это максимальное время, за которое система должна принять решение. Если время истекло, дальнейшая обработка запроса бессмысленна.

* Запрос от DSP: бюджет на выполнение **80 мс**. Если не уложились — отвечаем `No Bid`.
* Bidding Service -> Redis: таймаут **5–10 мс**.
* Delivery Service -> Bidding Service: таймаут **20 мс**.

## 2. Circuit Breaker

Базовое поведение для API Gateway описано в [api-gateway.md](./api-gateway.md).

Дополнительно Circuit Breaker применяется в Delivery Service при вызове Bidding Service. Если Bidding недоступен или деградирует, Delivery переключается на запасной сценарий (Fallback).

## 3. Retry Policy (Политика повторных попыток)

* Внешние запросы от DSP: **не повторяем**. Повторная ставка бессмысленна и только увеличивает latency.
* Внутренние gRPC вызовы (чтение кампаний): допускается ограниченный retry (2–3 раза) с экспоненциальной задержкой, так как операции идемпотентны.  
  > **Retry**: 2 попытки. Интервалы: 10 мс, 50 мс. Jitter: ±30%. Общий deadline: 80 мс.
* Kafka consumer: retry выполняется на уровне потребителя, но обязательна идемпотентная обработка.

## 4. Идемпотентность финансовых операций

События `Impression` / `Click` имеют уникальный `event_id`.

Financial Service проверяет `event_id` перед списанием средств. На уровне БД используется `UNIQUE(event_id)` или идемпотентный ключ.

Так как Kafka гарантирует доставку "at least once", дубликаты возможны, поэтому идемпотентность обязательна.

## 5. Резервные стратегии (Fallback)

* Если Redis недоступен — Bidding Service возвращает `No Bid` (безопасный режим).
* Если Bidding Service недоступен — API Gateway возвращает `No Bid` (не `503`), чтобы DSP-платформа не исключила нас из аукциона.
* Если ClickHouse недоступен — данные остаются в Kafka (retention), аналитика отстаёт, но не блокирует систему.

## 6. Failover и восстановление

| Компонент | Стратегия |
| -- | -- |
| Redis | Redis Sentinel + Master-Slave репликация |
| Kafka | Replication Factor = 3, min.insync.replicas = 2 |
| ClickHouse | ReplicatedMergeTree, шардирование |
| PostgreSQL | Patroni + Read Replica (детали в Task3) |

## Сценарии отказов

| Компонент | Влияние | Стратегия |
| -- | -- | -- |
| Bidding Service | Остановка ставок | API Gateway -> No Bid |
| Redis | Потеря данных кампаний | Fallback на No Bid |
| Kafka | Потеря событий | Буферизация, перезапуск |
| ClickHouse | Потеря аналитики | Данные остаются в Kafka |
| PostgreSQL | Потеря финансов | HA/реплика, запрет на списания |

## Итог

Надёжность достигается не попыткой избежать сбоев, а способностью быстро и безопасно деградировать.

* Критический путь (Bidding Service) защищён таймаутами и Fallback-стратегией.
* Данные событий защищены буферизацией Kafka.
* Деньги защищены идемпотентностью.

Это позволяет соответствовать SLA даже при частичной деградации компонентов.
