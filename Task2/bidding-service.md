# Спецификация сервиса ставок Bidding Service

Было принято решение выделить высоконагруженный RTB-сервис из монолита (ранее в монолите был функционал Auction Engine), чтобы соответствовать новым требованиям:

* минимизация времени отклика (Latency P95 80-100 мс)
* увеличение пропускной способности (Throughput 18 000 RPS)
* возможность гибко масштабироваться при увеличении нагрузки до 50 000 RPS
* изоляция сбоев и повышение устойчивости системы, чтобы не быть исключенными из аукциона
* сервис имеет свой ограниченный контекст.

## Границы сервиса

* приём запросов (Bid Request) на ставку от DSP-партнера
* валидация запросов
* подбор подходящих рекламных кампаний
* применение бизнес-правил (частотность, бюджеты, ограничения)
* расчёт оптимальную ставку
* выбор победителя
* возврат ответа (Bid Response) на ставку или "No Bid"
* НЕ хранит финансовые транзакции
* НЕ пишет статистику по событиям (клики/показы) в БД
* НЕ занимается аналитикой
* НЕ изменяет бюджеты (только проверяет лимиты)
* НЕ изменяет структуру кампаний (только читает данные)
* НЕ управляет интерфейсом рекламодателя

## Зависимости

* **Redis** (тип взаимодействия: Redis)  
  Только чтение данных о кампаниях, бюджетах, креативах.  
  Никаких синхронных вызовов к PostgreSQL в Hot Path
* **API Gateway** (тип взаимодействия: gRPC)  
  Приём внешних запросов от DSP-партнеров
* **Delivery Service** (тип взаимодействия: gRPC)  
  Прием запросов данных о победителе и отображаемом ему рекламном креативе
* **Система мониторинга и алертинга** (тип взаимодействия: Prometheus)  
  Отправка метрик (Latency, RPS, Error Rate) должна быть асинхронной.

**Важно**: Bidding Service работает в модели "Read Only". Обновление остатков бюджета и остановка кампаний происходит асинхронно через контур Financial Service. Financial Service в составе Legacy монолита получает данные от Delivery Service о том, что показ состоялся, обновляет данные в PostgreSQL, а уже посредством механизма CDC изменения доставляются в Redis, с которым работает Bidding Service.  
Задержка синхронизации бюджета допустима и нивелируется правилом "мягкого лимита". Таким же образом Bidding Service узнает и когда кампанию будет приостановлена. В таком случае, последующие запросы Bidding видят этот статус и возвращают No Bid.

## Модель данных

Сервис работает с объектами, оптимизированными для чтения, внутри Сервиса/Redis:

* сущность **Campaign**

    | Поле | Тип | Описание |
    | -- | -- | -- |
    | id | UUID | идентификатор |
    | name | string | название |
    | status | ENUM | статус |
    | targeting_rules | json | структурированный набор правил и ограничений (например, `os`, `country`, `placement_id` и т.д.) |
    | budget_limit | decimal | ограничения по бюджету |

* сущность **Creative**

    | Поле | Тип | Описание |
    | -- | -- | -- |
    | id | UUID | идентификатор |
    | name | string | название |
    | campaign_id | UUID | идентификатор кампании |
    | type | ENUM | banner/video |
    | size | numeric | размер контента |
    | content_url | string | URL для получения разметки с рекламой |

* сущность **BidRule**

    | Поле | Тип | Описание |
    | -- | -- | -- |
    | id | UUID | идентификатор |
    | campaign_id | UUID | идентификатор кампании |
    | priority | numeric |  |
    | base_bid | decimal | базовая ставка |
    | max_bid | decimal | максимальная ставка |

Сервис является stateless, он не отвечает за хранение этих данных, данными владеют специализированные сервисы, и они заносятся в Redis (Cache Warming), чтобы ускорить работу сервиса. Обновление кэша выполняется по событиям изменения кампаний (например, правила таргетинга, справочники, коэффициенты).

## API сервиса

Сервис реализует доступ по gRPC/Protobuf, как со стороны **API Gateway** (интерфейс взаимодействия с DSP-площадкой), так и со стороны **Delivery Service** (для запросов о победителях и данных креатива).

Контракт для взаимодействия с **API Gateway** продиктован и основан на данных стандарта **OpenRTB** (JSON/Protobuf), однако внутреннее взаимодействие с **API Gateway** происходит строго по бинарному Protobuf для экономии CPU и скорости сериализации.

* запрос от DSP **Bid Request**

    | Поле | Тип | Описание |
    | -- | -- | -- |
    | request_id | UUID | уникальный ID запроса |
    | dsp_id | UUID | идентификатор DSP |
    | context | object | сайт или приложение, где будет показана реклама, рекламная площадка и т.д. |
    | placeholder | object | информация о месте показа (размер баннера, позиция) |
    | device | object | тип устройства и местонахождение (Mobile/Desktop, IP, OS, Country) |
    | user | object | обезличенные данные о пользователе (сегменты, интересы) |
    | min_price | decimal | минимальная цена |
    | request_ts | timestamp | UTC таймстамп времени получения запроса |

* ответ DSP **Bid Response**

    | Поле | Тип | Описание |
    | -- | -- | -- |
    | response_id | UUID | уникальный ID запроса, на который сделан ответ |
    | bid_id | UUID | ID нашей ставки |
    | bids | list[object] | массив ставок |
    | | campaign_id | выбранная кампания |
    | | creative_id | креатив |
    | | price | размер ставки |
    | | status | NO_BID / ERROR / OK |
    | response_ts | timestamp | UTC таймстамп времени отправка ответа |

* запрос от Delivery Service **GetAdDecision**

    | Поле | Тип | Описание |
    | -- | -- | -- |
    | bid_id | UUID | ID запроса на показ |
    | session | object | Контекст пользователя (для проверки таргетинга) |

* ответ Delivery Service **AdDecisionResponse**

    | Поле | Тип | Описание |
    | -- | -- | -- |
    | status | ENUM | OK / NO_AD |
    | campaign_id | UUID | Победитель |
    | creative_id | UUID | Креатив |
    | markup_url | string | URL для получения разметки с рекламой |

## Нефункциональные требования

* **Latency**: P95 < 100 мс (внутренняя обработка)
* **Throughput**: пик 18 000 RPS
* **Scalability**: горизонтальное масштабирование, stateless
* **Availability**: допускается деградация ставок, например, в случае отказа Redis (fallback: No Bid)
* **Observability**: все запросы логируются (Response Time, Status, Rate)
